### 编辑入口

在项目目录中编辑 UTF-8 JSON。`knowledge/scenes.json` 保存地点及其活动引用，`knowledge/activities.json` 保存独立活动，`knowledge/rules.json` 保存产生式规则，`knowledge/departures.json` 保存行程结尾的离开选择。构建读取这些手工源，生成 `data/` 中供网页、引擎和 API 使用的目录、规则与图谱。

JSON 的说明写在 `_comment` 字符串中；文件中的现有条目可以直接作为模板。JSON 使用双引号，最后一项后面不加逗号，也不支持 `//` 注释。先保存文件，再运行构建。

### 地点与活动

地点名称写在 `place.name`，采用“商场”“Switch店”“剧本杀店”“泰山十栋玻璃房”等名词。一个去处可以支持多个活动。编辑现有去处时，直接调整该地点的 `activityIds`；不同真实地点可以引用同一个活动 ID。

本地自述支持的华农泰山区地点使用 `scauOnly: true`、`area: "campus"`、`place.universityId: "scau"` 与 `place.campusArea: "taishan"`。现有名称包括芷园食堂、泰山区12、15、16栋乒乓球桌、泰山超市与门口露天区、教四自习区与后坡路、泰山实验楼下花园、东区运动场外圈、宿舍间步道及综合体育馆后桥。说明保存原创摘要；`verificationStatus` 为 `awaiting_confirmation`，现实开放、供应和设施许可由现场确认。

地点的 `tags` 描述到场时已有的基本体验和场地特征。商场可以有 `indoor`、`daily`，所选电玩活动才带 `play`；桌游店的到场本身也按场地特征计分。费用单位为两人合计人民币，`load` 为设计负担单位。这些参数用于演示规划，实际价格、营业与设施需要确认。

`knowledge/scenes.json` 中每个地点的 `minutes` 是唯一耗时入口。活动均在该地点的固定时段内进行：同一地点选 0 个、1 个或多个活动，场景的起止时间都相同。活动仍按所选内容计算费用、体力、兴趣与资源依赖。需要延长或缩短某个地点的停留，修改该地点的 `minutes`。

当前设计时长包括商场 60 分钟、电影院 120 分钟、滑冰场 60 分钟、Switch 店 60 分钟、剧本杀店 90 分钟、泰山十栋玻璃房 45 分钟。地点固定时长属于规划模型参数，具体体验时长由实际安排确认。

下面是现有 Switch 店地点的完整编辑示例。修改对应条目时保留其 ID；新建不同去处时使用新 ID。

```json
{
  "id": "switch_store",
  "place": {
    "name": "Switch店",
    "kind": "ordinary",
    "category": "游戏体验店",
    "verificationStatus": "awaiting_confirmation"
  },
  "description": "用户提供的地点类型；具体店铺、营业和设备需要先确认。",
  "minutes": 60,
  "cost": [0, 0],
  "load": 0,
  "kind": "play",
  "area": "near",
  "indoor": true,
  "quiet": false,
  "tags": ["indoor", "daily"],
  "evidenceIds": ["E-user-switch"],
  "activityIds": ["switch_coop", "switch_race"]
}
```

`place.kind` 通常为 `ordinary`。顶层 `kind` 是引擎使用的体验类别，例如 `explore`、`play`、`meal`、`culture`。`rest` 是原地休息的特殊地点：`place.kind` 为 `休息`，顶层 `kind` 为 `rest`，`area` 为 `current`，`activityIds` 为 `[]`。公共休息区承载交谈、听歌等可选活动。

活动在独立表中定义一次。下面是 `switch_coop` 的示例，可在 `knowledge/activities.json` 中修改费用、负担、兴趣和说明。

```json
{
  "id": "switch_coop",
  "title": "玩一个合作关卡",
  "description": "选双方接受的合作游戏，设备和游戏需先确认。",
  "cost": [30, 60],
  "load": 1,
  "group": "play",
  "mode": "multi",
  "novelty": 55,
  "tags": ["play"],
  "evidenceIds": ["E-user-switch"]
}
```

活动手工源及 `activityOverrides` 均不设置耗时字段。编译后的活动统一为 `minutes: 0`、`compositionMode: "included"`、`durationMode: "within_scene"`，目录声明 `durationPolicy: "scene_only"`。`included` 表示活动安排在场景固定时段内；所选活动的费用和体力按数据正常核算。构建器会拦截手工添加的活动 `minutes`、`duration`、`durationMinutes`、`compositionMode` 或 `durationMode`，并提示修改场景时长。

`mode: single` 表示同一个 `group` 内只选一项；需要双方明确愿意的玩法设 `requiresExplicitConsent: true`。准备、资源及先行关系使用下表字段。

| 字段 | 用途 |
| --- | --- |
| `requires` / `preconditions` | 执行前需要具备的资源或确认事项。 |
| `preparationIds` | 展示给用户的准备事项 ID。 |
| `provides` / `consumes` | 执行后产生或消耗的资源。 |
| `predecessorIds` | 必须先完成的地点或活动 ID。 |
| `exclusiveKey` | 同一行程中互斥的体验，例如 `main_meal`。 |
| `dietaryTags` | 供明确饮食限制匹配的标签。 |
| `windows` | 设计时间窗，使用当天的 `startMinute` 与 `endMinute`。 |

泰山十栋玻璃房的到场基本体验为 `explore`，固定安排 45 分钟。`glass_noodle`、`glass_burger` 分别计入正餐费用与体力，并通过 `provides: ["meal_completed"]` 标识完成正餐；两者共享 `exclusiveKey: "main_meal"`。所选正餐与桌游都在这 45 分钟内安排。

电影院和滑冰场的到场费用为零，观影票价计入 `film_pick`，滑冰票价计入 `ice_slow` 或 `ice_practice`。这些是设计区间。电影院到场要求 `opening_checked`；球拍、球和合适的鞋等器材要求跟随对应运动活动。修改票价时调整收费活动的 `cost`，一次体验的费用在一个位置核算。

### 四餐地点与用餐活动

时段规划使用 `scene.mealRoles` 选择用餐地点，允许值为 `breakfast`、`lunch`、`dinner`、`supper`。这个数组表示项目设计中适用的餐次，现实供应和营业仍需确认。校园食堂和泰山十栋玻璃房支持早餐、午餐与晚餐；餐馆、粤式茶楼和校内西式餐馆支持午餐与晚餐。烧烤摊和小吃街是用户指定的宵夜地点类型，具体位置、营业、菜单与座位待确认。早餐集合前已吃的 `pre_meeting` 和宵夜 `skip` 由规划界面提供选项。

用餐活动的 `mealRoles` 声明该菜单适用的餐次。早餐使用两人 10 至 20 元的早餐活动，费用属于设计区间。购买明早早餐的 `breakfast_pack` 提供携带物资；实际吃早餐的 `breakfast_eat` 提供 `meal_completed`。专门用餐阶段按所选餐次筛选活动，并必须选择实际提供 `meal_completed` 的活动。地点到场费用与负担为基础参数，套餐费用和用餐恢复负担计入活动；食物限制根据所选活动的 `dietaryTags` 过滤，并需核对现实食材及过敏原。

编译器为每个地点生成 `mealActivityIds`，其内容是该地点提供 `meal_completed` 的活动 ID。引擎可用它定位候选，再按活动 `mealRoles`、预算、体力、准备和饮食限制筛选。每个地点声明的餐次须至少有一个适用用餐活动；空场馆到场不产生用餐目标。手工源编辑 `activityIds` 与活动属性即可，`mealActivityIds` 随构建生成。用餐活动统一为零耗时的 `included` 活动，地点的 `minutes` 继续决定整段停留时长。

饭点设计窗口由引擎按时段生成。当前宵夜地点的 `windows` 为 `[]`，具体营业需出发前确认。新增跨午夜的设计窗口时须遵循规划器当天与次日时间的表示约定；源知识的窗口范围为当天 0 至 1440 分钟，不能用超过 1440 的数字表示已核实营业。

### 同一活动在不同地点的差异

`boardgame_coop`、`boardgame_cards` 同时挂在桌游店和泰山十栋玻璃房。桌游店使用独立活动表中的费用；玻璃房通过地点内的 `activityOverrides` 设置自带游戏及场地许可要求。下面的片段放在玻璃房地点对象中，其 `activityIds` 也须包含 `boardgame_cards`。

```json
"activityOverrides": {
  "boardgame_cards": {
    "cost": [0, 0],
    "requires": ["boardgame_kit", "venue_checked"],
    "preconditions": ["boardgame_kit", "venue_checked"],
    "preparationIds": ["boardgame_kit", "venue_checked"],
    "evidenceIds": ["E-G001", "E-user-glass-boardgame"]
  }
}
```

override 中写出的数组会替换该活动原数组，因此需要保留的证据和准备项应完整列出。活动 ID 由独立表维护，地点增量只能调整内容和参数。编译后的地点仍有内嵌 `activities`，独立导出的活动列出所有 `allowedSceneIds`；图谱通过地点活动边和场地变体节点记录这些差异。

### 行程离开选择与城市费用档位

`knowledge/departures.json` 编译为 `catalog.departures` 数组，默认 ID 由文件中的 `defaultId` 指定，并导出为 `catalog.defaultDepartureId`。当前默认值为 `separate`，表示各自回去，告别与离开预留10分钟、费用为 `[0, 0]`；`walk_together` 表示明确选择后一起走一段，预留20分钟、费用为 `[0, 0]`。这些固定分钟属于结尾模型，实际交通需另行确认。离开数据独立于 `catalog.scenes`，图谱节点类型为 `departure`。

`hotel` 表示过夜安排中用户明确选择共同入住酒店，声明 `onlyOvernight: true` 与 `requiresExplicitChoice: true`。消费方须先检查明确选择与过夜条件，再将费用和15分钟入住预留纳入结尾核算。这个时长用于办理入住，房费按双人一间客房一晚计算。酒店选项通过独立目录交给消费方，行程默认使用 `separate`。

输入 `cityTier` 的允许值为 `tier1`、`tier2`、`tier3`，默认 `tier1`。条件表登记该输入，`metadata.defaultContext.cityTier` 保存默认值；运行时目录提供 `catalog.cityTiers` 和 `catalog.defaultCityTier`。离开选择输入 `departureChoice` 的默认值为 `separate`，条件表和 `metadata.defaultContext.departureChoice` 与离开目录的默认 ID 一致。界面与引擎接入时从这些字段读取默认值，并验证枚举。

酒店的 `costByCityTier` 使用以下结构，单位由 `costUnit: "CNY_per_room_for_two_per_night"` 声明。费用与时长的证据使用 `assertionKind: "designed"`，`parameterStatus` 为 `designed_not_measured`；当前报价与房源需要单独确认。

```json
"costByCityTier": {
  "tier1": [200, 400],
  "tier2": [150, 300],
  "tier3": [100, 250]
}
```

构建器检查三种离开 ID、免费项费用、酒店限制、城市档位完整性及设计证据引用。修改离开字段后重新构建，内容修订指纹随目录自动更新。

### 规则、证据和元数据

`knowledge/rules.json` 中，`when.all` 表示全部条件满足，`when.any` 表示至少一个条件满足，`then` 保存命中后的动作。编辑现有 `R-rain-indoor` 时可以使用下面的格式。

```json
{
  "id": "R-rain-indoor",
  "title": "雨天优先室内候选",
  "priority": 89,
  "strength": "soft",
  "when": {
    "all": [
      {"fact": "context.weather", "op": "eq", "value": "rain"},
      {"fact": "scene.indoor", "op": "eq", "value": true}
    ]
  },
  "then": [{"action": "prefer_scene", "amount": 12}],
  "evidenceIds": ["E-G002"],
  "evidence": ["E-G002"],
  "assertionKind": "designed",
  "parameterStatus": "designed_not_measured",
  "enabled": true
}
```

新增地点、活动或规则时，需要选择合适的依据 ID。`knowledge/evidence.json` 保存原创摘要、来源定位和核对边界。仅由用户提供名称或玩法的内容使用 `sourceKind: "user_design"`、`assertionKind: "designed"`、`sourceDocumentId: null`、`reviewStatus: "awaiting_confirmation"`，并写明现实信息待确认。现有 `E-user-switch` 等记录提供了完整模板。待确认地点的地址和营业时间留空。

`knowledge/source-registry.json` 保存 151 份原始资料的登记、哈希与采用证据关系。引用本地语料时保留行号和锚点哈希，摘要使用原创措辞。公开目录不包含语料原文，原始资料仍在项目外的语料目录中。`knowledge/metadata.json` 管理版本、兴趣标签、资源标签和显示选项；新增准备资源时也更新 `knowledge/conditions.json` 的 `preparedIds.allowedValues`。

### 一键构建与检查

在 `datemate` 项目目录运行以下命令即可构建并校验全部引用、规则及图谱。

```bash
node tools/build_catalog.mjs
```

构建会先完成全部验证，再写入 `data/catalog.json`、`data/catalog.mjs`、`data/activities.mjs`、规则、图谱、证据、来源登记、条件与构建报告。地点和活动的 ID 必须唯一，所有活动须挂到地点，证据、资源和先行活动须可解析。构建失败时根据报错中的文件字段及 ID 修改源，再运行命令。

保存手工源、检查编译文件是否同步，可以运行：

```bash
node tools/build_catalog.mjs --check
node --test tests/knowledge.test.mjs
```

`--check` 只读取文件，并检查编译结果的字节一致性。知识测试检查地点定义、共享玩法的场地差异、静态引用与公开摘要边界。设置 `DATEMATE_PYTHON` 后，还会检查旧语料脚本的覆盖保护；未设置时该项测试标为跳过。完整引擎测试由项目的 `npm test` 执行。

原始语料候选抽取使用显式的独立输出目录：

```bash
python tools/build_knowledge.py --extract-candidates --output ../knowledge-candidates-20261014
```

候选目录应为新的空目录。抽取器会拒绝默认运行、已有候选文件，以及项目根目录、`data/`、`knowledge/` 下的输出。候选需要人工核对，再将适用条目合入手工源并执行编译。项目的日常更新入口始终是 `tools/build_catalog.mjs`。

地点、活动、离开选择或规则语义发生改变时更新 `knowledge/metadata.json` 中的版本。当前知识版本为 `knowledge-4.1.0`，运行时 schema 为 `place-activity-4.0`。

### 双击重建与复盘修订

也可以直接双击项目根目录的 `重建知识库.cmd`。它依次验证并编译知识源、生成离线HTML；失败时显示具体JSON字段，修正后再次运行。文件编译成功后刷新本地页面即可看到变化。要更新GitHub Pages，需要再提交并推送源码与编译产物。

每次内容编译都会自动产生修订指纹。旧复盘通过版本与内容修订共同识别知识变化，日常手工编辑后的构建会自动更新该指纹。
